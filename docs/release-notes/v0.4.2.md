# xrFPS 0.4.2

Fixes for the Control Center not opening at all on machines that never had
its runtimes installed — the "I click the exe and nothing happens" reports.

## Fixed

- **The app required a .NET 9 runtime the release never shipped.** Since
  .NET 8, setting a `RuntimeIdentifier` no longer makes `dotnet publish`
  produce a self-contained build, so v0.4.1 quietly became framework-dependent:
  it needed the .NET 9 runtime preinstalled, Windows does not ship one, and
  neither the installer nor the portable zip provided or checked for it. On a
  machine without it the exe put up (at best) a runtime-download prompt and
  exited. The app now publishes fully self-contained, and the release script
  refuses to package a build that is missing the bundled runtime. The
  download is larger; it also works.

- **The VC++ runtime was likewise assumed rather than shipped.** Both the
  self-contained Windows App SDK and `xrfps_core.dll` link the dynamic CRT,
  which a clean Windows install lacks. Without it the process died during
  startup with no dialog of any kind. The release now carries the VC++
  runtime DLLs app-locally, next to the exe, so the installer and the
  portable zip work on a bare machine.

- **Startup failures were invisible.** A GUI process that fails before its
  window exists simply exits; nothing told the user (or us) what went wrong.
  Any failure to start now shows an error dialog — drawn with plain Win32, so
  it works even when the UI stack itself cannot load — and appends the full
  exception to `%LOCALAPPDATA%\xrFPS\startup-crash.log`, which a bug report
  can attach.

## Install or update

The Control Center offers this update in the app — though anyone hit by this
bug never got that far: download and run `xrFPS-0.4.2-Setup.exe`, or extract
the portable ZIP complete.
